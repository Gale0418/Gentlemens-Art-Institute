# 大型書庫掃描進度修復（2026-09-09）

## 問題與變更

原本檔案發現完成後，仍須等待整批檔案指紋與詳細資料處理，再一次寫入書架；畫面只停在已發現本數，無法區分正在整理或狀態查詢失聯。

- 書架索引每 64 本提交並回報實際處理數；成功完成最後一批後才將未再出現的位置標記離線。中斷時保留已提交批次及尚未確認的舊書。
- iOS 外部資料夾自動整理只使用已發現的檔案資訊與現有資料庫，避免自動內容讀取觸發 Files provider 下載。新書先使用檔名資料；已有詳細資料、覆寫、閱讀進度與指紋保留。詳細資料可按需重新匯入。
- Mac 與其他來源維持完整詳細資料處理，改為分批提交。
- 新增 migration 7，為書本位置的 `(comic_id, online)` 建立索引。原本最後離線判定會逐本全表掃描；新索引也改善單本位置查詢，舊資料庫會自動升級。
- 進度區分檔案掃描、書架整理、完成及失敗；繁體中文、英文與日文同步更新。
- 狀態查詢超過 5 秒提示暫時無法取得狀態；跨輪詢重啟仍只容許一筆未完成原生請求，避免堆積。逾時不冒充掃描完成，較舊回覆不得覆蓋新掃描。

- 完整 `npm test` 通過，包含 588 個翻譯鍵、pending 原生請求、晚到回覆、錯誤提示及掃描狀態相容性。
- 完整 Rust library tests：128 passed、0 failed、1 ignored；涵蓋部分提交可讀、取消保護、完成後移除舊位置，以及 ID／metadata／進度／指紋保留。

## 限制與依據

沒有取得造成現場等待的特定檔案或執行緒堆疊，因此不將某一個檔案供應商宣稱為已證實根因。合成索引時間不等於 iPad 真實目錄掃描時間。

[Tokio 官方文件](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html) 說明已開始的 blocking task 無法以 abort 取消；本次取消在可控批次邊界檢查，不宣稱能中斷底層檔案讀取。[SQLite 交易文件](https://www.sqlite.org/lang_transaction.html) 支持短交易與單一寫入者的設計取捨。
